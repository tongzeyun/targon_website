# SmartSale / 灵眸智售迁移精简方案

日期：2026-10-10。状态：代码静态检查完成，待确认实施范围。

## 分析与假设

- 来源项目：`D:/T_workspace/saleseye`；目标项目：`D:/T_workspace/TargonWebsite`。
- 当前代码中的业务模块名称和路径是 Smart Eye / `/smart-eye`，本文将其视为用户所说的 SmartSale。
- 目标项目的 `/smart-eye` 是占位页，尚未迁移业务代码。
- 来源项目包含 16 个业务页面和 48 个 API route 文件。API 数量包含认证、健康检查和内部任务入口，并非全部是用户功能。
- 默认保留既有账号、组织数据范围、API 契约、数据库结构、第三方配置和任务行为。
- 本轮为静态代码检查，尚未验证数据库、实际部署、移动端或第三方服务。未读取环境文件中的凭证，未修改新旧项目业务代码。
- “不减少功能”以当前代码实际可达的行为为基线，文档描述及未使用的实现不能单独作为已实现功能的证据。

## 已确认的问题及拟议变更

### 1. 同一 API 请求重复验证 JWT

证据：来源项目 `src/proxy.ts:205` 的业务 API 分支验证 JWT；路由通过 `src/lib/api/auth.ts:104` 的 `getAuthOrg()` 再调用 `authenticateRequest()` 验证同一个 Cookie。

方案：保留路由层作为业务 API 的身份认证边界，删除 Proxy 中重复的 JWT 检查。采用一个小型、统一的路由认证入口，负责返回认证失败响应，业务 handler 只接收认证上下文。Proxy 保留有实际用途的公共请求处理。

风险与先决条件：不能仅删除 Proxy 检查。部分路由直接调用会抛出 `AuthError` 的 `getAuthOrg()`，没有捕获该错误；否则原来返回 401 的请求可能变成 500。必须先覆盖所有受保护 handler 的错误响应。用户、组织信息仍从验证后的 Cookie 获取，不能信任客户端传入的身份请求头。

验收：直接访问受保护 API，缺少、伪造或过期 Cookie 都返回 401；合法请求只执行一次 JWT 验证；Cookie 写请求的来源检查仍然有效。

### 2. 未使用的页面认证门和登录初始化分支

证据：`src/app/(website)/smart-eye/_components/smart-eye-auth-gate.tsx` 定义 `SmartEyeAuthGate`，在来源项目 `src`、`scripts` 的生产代码中没有发现使用方。其调用的 `resolveBrowserAuthSession()` 也没有其他生产调用方。

方案：不迁移该未使用组件及其专属初始化、刷新分支。保留 `browser-auth.ts` 中登录页使用的安全回跳函数，以及设置页使用的退出登录函数。继续通过实际业务请求处理登录失效。

取舍：这一清理减少代码和未来维护负担；因为当前组件未挂载，不能将其宣称为已确认的页面性能问题。

验收：登录、注册、退出、会话失效后的回跳路径一致；临时服务故障不会被误判为退出登录；现有自动刷新中的并发合并和有限重试保留。

### 3. 同样的任务类型列表重复维护

证据：`src/app/api/jobs/route.ts:13` 和 `:30` 中允许列表、可创建列表当前完全相同；`src/lib/jobs/worker.ts:78` 再维护一份相同的支持列表。

方案：将现有任务类型统一到一个共享定义，API 和 Worker 消费同一份列表。保留所有现有任务 handler，不引入通用工作流引擎，不改变任务 payload 或重试规则。

验收：当前 15 种任务类型保持可创建、可执行；未知类型仍被拒绝；任务进度、失败、取消和完成状态保持原有行为。

### 4. 历史兼容和无调用代码

证据：来源项目 `src/lib/ai/key-store.ts` 的导出函数未发现生产引用；`src/lib/db/queries.ts` 是历史重导出层，未发现生产 import；`src/lib/db/index.ts:8` 中弃用的 `initDb()` 未发现生产调用。

方案：不迁移经引用检查确认无调用的兼容层、函数和对应的孤立测试。保留实际被调用的数据库与 repository 接口。

风险：静态引用检查不覆盖仓库之外的消费者；迁移时须补查部署脚本、动态加载及相关消费者。不删除仍承载业务行为的兼容路径。

### 5. AI 客户端初始化重复

证据：`src/lib/ai/client.ts:74` 的 `getAIClient()` 和 `:89` 的 `ensureClient()` 重复处理同一 DeepSeek 环境配置和客户端单例。

方案：只维护一份客户端初始化逻辑；依据实际调用方保留需要的同步或异步接口。保留模型配置、超时、网络重试和现有服务边界。

取舍：精简内部实现不要求更换模型提供商、SDK 或重写 AI 业务流程。

## 限流和校验的边界

目前并未发现业务 API 广泛使用基于角色的权限门。`role` 字段和 `organizationId` 身份信息本身不构成可直接删除的冗余权限系统。

现有限制承担不同责任：

| 检查 | 实际用途 | 本轮处理 |
| --- | --- | --- |
| 登录、注册限流 | 限制密码尝试和批量注册 | 保留 |
| API 提交频率限制 | 限制短时间任务提交 | 保留规则，减少各路由重复接线 |
| 创建任务前的额度检查 | 尽早反馈额度不足 | 保留，不能与执行时检查简单互相替代 |
| Provider 每日额度与并发租约 | 多进程实际调用准入、计数和并发控制 | 保留 |
| 写请求 Origin 检查 | Cookie 请求的 CSRF 防护 | 每条适用路径保留一次有效检查，避免认证路由与 Proxy 重复 |
| SQL 组织范围与更新字段白名单 | 数据归属及防止修改身份字段 | 保留 |
| 文件格式、大小及读取范围检查 | 文件处理和下载边界 | 保留 |
| AI 输出解析及结构校验 | 防止坏输出进入业务与文档生成 | 保留 |

如果希望取消每日额度或放宽请求频率，需要另外明确产品规则；这会改变行为，不能包装成无功能影响的代码清理。

数据库任务、Worker、任务恢复、文件持久化、文档历史、审阅确认和 AI 调用记录都有实际用途，保留。数据库只有 PostgreSQL，但已有 adapter/repository 边界较小，第一轮不为减少文件数量而拆除。

现有 CORS 配置包含移动端开发来源。未确认外部客户端需求之前，不删除跨端兼容行为，也不将旧开发地址自动视为新生产配置。

## 实施顺序

1. 建立可达功能、API 和运行配置清单，将现有测试映射到迁移后的行为；确认数据库及文件存储沿用方式。
2. 在目标项目迁移实际使用的业务代码、资源和必要依赖，同步完成以上五项精简及重复来源检查收敛。来源项目作为对照保留。
3. 按完整业务链路回归。涉及外部服务的验证使用实际可用环境，报告无法验证的部分，不以 mock 测试代替服务可用性结论。

不更改已迁移官网页面，不改数据库业务结构，不新增架构框架。依赖只按实际调用加入，逐项说明用途，不整包照搬旧 `package.json`。
